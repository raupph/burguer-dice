Especificação do Trabalho Prático Final
1. Objetivo
Este trabalho visa proporcionar aos alunos a oportunidade de integrar, em um sistema real, as
estruturas de dados estudadas ao longo da disciplina. O trabalho exige não apenas o uso correto
das estruturas, mas também a medição e análise comparativa do desempenho de operaçõeschave, relacionando os resultados à teoria vista em aula. A nota corresponde a 15% da nota final
da disciplina.
2. Reaproveitamento de código
As implementações das estruturas de dados desenvolvidas ao longo da disciplina foram dadas em
aula e devem ser usadas como ponto de partida — o objetivo não é reimplementá-las do
zero. O grupo deve adaptá-las e organizá-las conforme julgar adequado: ajustar a interface de
funções, adicionar campos às estruturas, reorganizar módulos, renomear identificadores, compor
TADs entre si, etc. A qualidade dessas decisões de projeto é um critério de avaliação; qualquer
modificação relevante deve ser descrita e justificada no relatório.
O trabalho pode ser desenvolvido em linguagem C ou C++. Não é permitido utilizar estruturas de dados prontas de bibliotecas externas ou da linguagem padrão (como std::map,
std::priority_queue, std::unordered_map, std::stack, std::queue ou similares). Todas as
estruturas devem ser as da disciplina, vistas em aula, podendo ser adaptadas.

O trabalho deverá ser realizado em duplas (fortemente recomendado) ou individualmente.
O jogador é o mais novo funcionário do Dado Burger (Figura 1) e deverá atender aos pedidos
de uma série de clientes ao longo do dia.

3.1. Menu e histórico
A tela inicial deve ser um menu com três opções: Novo jogo, Como jogar e Histórico.
A opção Como jogar exibe uma tela estática com as regras básicas: o objetivo do jogo, a lista de

O histórico registra em arquivo o nome e a pontuação de cada jogo encerrado. Ao abrir o histórico,

3.2. Parâmetros configuráveis
Os valores abaixo ficam a critério do grupo e devem ser documentados e justificados no relatório.
Não há resposta certa: o grupo deve equilibrar jogabilidade e desafio.

3.3. Turnos e clientes
O jogo é baseado em turnos: cada ação do jogador consome um turno.
Pedidos. Para cada cliente, um código de pedido é sorteado aleatoriamente dentro do intervalo
de pedidos disponíveis na AVL e buscado de maneira eficiente. Este é o pedido que o jogador
deverá atender para aquele cliente.
Fila de clientes. Todos os clientes da partida são enfileirados no início do jogo, na ordem de
chegada. O jogador sempre atende o cliente na frente da fila. Ao concluir o pedido desse cliente,
ele é removido da fila e o próximo passa à frente.
Paciência. Cada cliente tem uma paciência máxima (em turnos, definida pelo grupo). A
paciência do cliente da frente da fila é decrementada após cada ação do jogador que consome
um turno. A paciência dos demais clientes na fila não é decrementada enquanto aguardam.
Derrota. Se a paciência do cliente da frente chegar a zero antes de o pedido ser concluído, o jogo
encerra imediatamente. A pontuação é o número de clientes atendidos até aquele momento.
Vitória. Se todos os clientes forem atendidos sem que nenhum perca a paciência, o jogador
vence. A pontuação é o número total de clientes atendidos.
Os clientes aguardam atendimento em uma fila (FIFO) (ver §4).
3.4. Ações do jogador
As seguintes ações consomem um turno cada:
• Preparar um ingrediente
• Adicionar um ingrediente ao hambúrguer

• Remover o ingrediente do topo do hambúrguer
Ações de consulta (ver estoque, ver pedido, etc.) não consomem turno.

4.1. AVL — armazenamento dos pedidos
Cada pedido é identificado por um código numérico único e representado em duas linhas no
arquivo: a primeira é o código; a segunda é uma string de 5 a 7 caracteres com a receita (Tabela 1).
▶ Os pedidos devem ser carregados em uma AVL na inicialização do programa, antes
de exibir o menu, a partir do arquivo recebido via linha de comando (ver Apêndice C).
O código foi dado em aula. O formato do arquivo está descrito em §6.
4.2. Lista contígua — histórico de partidas
▶ O histórico lido de historico.txt deve ser carregado em uma lista contígua alocada
dinamicamente na inicialização do programa, antes de exibir o menu, a partir do
arquivo recebido via linha de comando (ver Apêndice C). Cada entrada contém o nome
do jogador e a pontuação obtida.
A escolha da lista contígua é intencional: os algoritmos de ordenação das aulas operam sobre
ela e permitem acesso por índice em O(1), o que é necessário para implementações eficientes de
quicksort e mergesort. Ao encerrar uma partida, a nova entrada é acrescentada ao final da
lista e salva no arquivo.
Integridade dos dados. A ordenação utilizada para exibição ou para as medições de desempenho não deve modificar o arquivo historico.txt. Ao gravar uma nova entrada, todas as
partidas anteriores devem ser preservadas no arquivo.
4.3. Tabela hash — cache de pedidos
▶ O programa deve manter uma tabela hash, indexada pelo código do pedido, como
cache das buscas realizadas durante a sessão. O código foi dado em aula. A política de
tratamento de colisões recomendada é encadeamento separado (cada posição contém
3
uma lista encadeada das entradas que mapearam para aquele índice); o grupo pode
adotar outra política e implementá-la.
A lógica de acesso é: ao sortear um código para o novo cliente, consulta-se primeiro a tabela hash;
se o pedido já estiver no cache (hit), ele é retornado sem consultar a AVL; se não estiver (miss),
busca-se na AVL e o resultado é inserido na hash.
Convenções para as métricas da hash:
• Colisão: ocorre quando uma inserção encontra a posição já ocupada por ao menos uma
entrada. Conta-se uma colisão por inserção que gera conflito, independentemente do comprimento da lista naquele índice.
• Fator de carga: λ = n/m, onde n é o número de entradas ocupadas e m é o tamanho da
tabela.
• Redimensionamento: não é obrigatório e não faz parte dos requisitos deste trabalho.
4.4. Lista encadeada — receita de cada pedido
▶ A receita de cada pedido deve ser armazenada como uma lista encadeada, onde
cada nó representa um ingrediente na ordem de montagem (de baixo para cima). Esta
representação permite percorrer os ingredientes em ordem e verificar o hambúrguer montado pelo
jogador. Use o código das aulas.
4.5. Pilha — montagem do hambúrguer
▶ A montagem do hambúrguer deve ser gerenciada por uma pilha (LIFO): adicionar um ingrediente equivale a empilhá-lo; remover o ingrediente do topo equivale a
desempilhá-lo. Só deverá ser aceito o hambúrguer cuja pilha, lida de baixo para cima, corresponda exatamente à lista encadeada do pedido. Use o código das aulas.
O pão de baixo já começa no prato (não faz parte da receita). Não deve ser possível adicionar
ingredientes por cima do pão de cima.
Verificação da receita. Como a interface padrão da pilha não permite percorrê-la de baixo
para cima sem desempilhar, o grupo pode: (a) adaptar o TAD para adicionar uma operação de
travessia, ou (b) usar uma estrutura auxiliar temporária (cópia, vetor, etc.) para a comparação,
preservando a pilha original ao final. Qualquer abordagem é válida desde que a pilha não seja
destruída numa consulta.
4.6. Fila — clientes
▶ Os clientes devem ser gerenciados por uma fila (FIFO): clientes entram no final e
são atendidos na ordem de chegada. Use o código das aulas.
4.7. Heap mínimo — ingredientes perecíveis
Ingredientes são divididos em três categorias:
• Sem preparo, quantidade infinita: ketchup, mostarda, alface, picles, pão.
• Com preparo, perenes: queijo suíço, queijo cheddar, cebola, tomate. Cada ação de
preparo produz uma unidade no estoque. Uma vez preparados, aguardam indefinidamente.
• Com preparo, perecíveis: carne, ovo frito, bacon. Uma vez preparados, devem ser descartados após um número de turnos definido pelo grupo (pode ser diferente por ingrediente).
4
▶ O estoque de cada ingrediente perecível deve ser implementado como um heap
mínimo (um por tipo: carne, ovo frito, bacon), com prioridade no turno de validade
— o ingrediente mais próximo de vencer fica sempre no topo. Use o código das aulas.
Regras de validade:
• O turno de vencimento de uma unidade é: turno de preparo + validade configurada.
• No início de cada turno, antes de qualquer ação do jogador, o programa verifica o topo
de cada heap perecível e descarta todas as unidades com turno de vencimento ≤ turno atual,
repetindo até o heap estar vazio ou o topo ser válido.
• Ao consumir um perecível, retira-se a unidade do topo do heap correspondente (a que
vence primeiro). Se o heap estiver vazio, a ação não pode ser realizada.
Caso um ingrediente já usado no hambúrguer seja removido pelo jogador, ele é descartado e não
volta ao estoque.

5. Medições obrigatórias e Relatório de Desempenho
O programa coleta métricas ao longo de toda a execução e as consolida em dois momentos:
imediatamente após o carregamento dos pedidos e ao encerrar a partida, quando é exibido
automaticamente um Relatório de Desempenho completo — tanto na tela quanto gravado em
arquivo.
Arquivo de log obrigatório. Todas as medições devem ser gravadas em medicoes.log,
criado (ou sobrescrito) a cada execução. O arquivo deve registrar cada métrica com seu nome
e valor, de forma legível, para consulta após o encerramento do programa. A ausência do
arquivo ou a omissão de qualquer métrica implica desconto no critério Medições obrigatórias.

5.1. Após o carregamento: AVL e histórico
Logo após o carregamento inicial, registrar as métricas abaixo no log.
AVL:
• Número de nós inseridos
• Altura da árvore resultante
• Número de rotações (inserção)
• Tempo total de carregamento
Histórico (lista contígua) — contexto:
• Número de entradas carregadas
Convenções:
• Altura: árvore vazia = 0; árvore com apenas a raiz = 1.
• Rotações: uma rotação dupla conta como duas rotações simples.
• Comparação (busca): cada comparação entre a chave procurada e a chave de um nó
visitado conta como uma comparação.
• Média de comparações por busca: se não houver nenhuma busca na partida, reportar
0.
Durante a partida, acumule silenciosamente (sem exibir a cada turno) o tempo total e o
número de comparações das buscas na AVL. Esses dados serão exibidos apenas no Relatório
de Desempenho.
5.2. Relatório de Desempenho (ao encerrar a partida)
Ao encerrar a partida — seja por vitória, derrota ou saída voluntária — o programa exibe automaticamente o Relatório de Desempenho e o grava no log antes de retornar ao menu. O relatório
deve conter:
1. AVL — buscas durante a partida:
• Total de comparações e média por busca;
• Tempo total acumulado de buscas.
2. Tabela hash — estatísticas de cache:
• Total de hits e misses; taxa de acerto (%);
• Fator de carga (λ = n/m);
• Total de colisões durante inserções.
3. Ordenação do histórico (executada quando o usuário acessa a opção Histórico no menu):
• O algoritmo ordena uma cópia independente do conjunto de dados — a cópia fica
fora do intervalo cronometrado;
• Tempo de execução do algoritmo escolhido;
• Em acessos subsequentes ao Histórico, a medição é repetida e o log atualizado.

A. Medição de tempo: referência prática
Os arquivos abaixo são distribuídos junto com o material da disciplina. Basta copiá-los para o
projeto e incluí-los na compilação (ver Apêndice C).
Versão C
timer.h
# ifndef TIMER_H
# define TIMER_H
# include < time .h >
typedef struct { clock_t inicio ; } Timer ;
void timer_iniciar ( Timer *t) ;
double timer_parar ( Timer * t) ; /* retorna tempo em segundos */
# endif
timer.c
# include " timer .h "
void timer_iniciar ( Timer * t) { t -> inicio = clock () ; }
double timer_parar ( Timer * t) {
return ( double ) ( clock () - t -> inicio ) / CLOCKS_PER_SEC ;
}
Versão C++
timer.hpp
# ifndef TIMER_HPP
# define TIMER_HPP
# include < chrono >
struct Timer { std :: chrono :: steady_clock :: time_point inicio ; };
void timer_iniciar ( Timer *t) ;
double timer_parar ( Timer * t) ; /* retorna tempo em segundos */
# endif
timer.cpp
# include " timer . hpp "
void timer_iniciar ( Timer * t) {
t -> inicio = std :: chrono :: steady_clock :: now () ;
}
double timer_parar ( Timer * t) {
auto fim = std :: chrono :: steady_clock :: now () ;
return std :: chrono :: duration < double >( fim - t -> inicio ). count () ;
}

Configuração do exemplo

Pré-jogo: carregamento
Os pedidos são lidos de argv[1] e inseridos na AVL; o histórico é lido de argv[2] e carregado
na lista contígua (neste exemplo, 15 entradas). O programa grava no medicoes.log:

Entradas carregadas 15
A tabela hash começa vazia. Os heaps dos perecíveis começam vazios.
Cliente 1 — pedido 1001: nkmpz
Início do atendimento. C1 está na frente da fila. O código 1001 é sorteado.
• Hash: MISS (tabela vazia) → busca na AVL: 2 comparações → receita nkmpz encontrada.
• Pedido inserido na hash: {1001 → nkmpz}.
Os turnos seguintes montam o hambúrguer nkmpz (preparar carne + adicionar n, k, m, p, z).

Caso: perecível não usado a tempo
Com validade de 3 turnos, o jogador prepara três carnes seguidas:
• T1: prepara carne → validade = turno 4. Heap: [ 4 ]
• T2: prepara outra → validade = turno 5. Heap: [ 4, 5 ]
• T3: prepara mais uma → validade = turno 6. Heap: [ 4, 5, 6 ]

• T4 (ação): usa carne → remove topo (5). Heap: [ 6 ]

int main ( int argc , char * argv []) {
